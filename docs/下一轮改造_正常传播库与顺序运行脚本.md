### 1.1 应先修复的源码问题

以下是静态调用链审查结论，需在实现轮先加入暴露问题的回归测试。

1. **准备快照没有完整约束启动输入。** `execution/benign_collection.py:501` 的 `collect_benign_live` 只确认 `preparation_manifest.json` 存在，并比较配置 JSON；没有解析该 manifest、核验其自哈希、run identity 和记录的场景/prompt 哈希。prepare 后修改同一路径的场景或 prompt 不会被这里的配置比较发现。配置引用的 profile/registry/bridge/patch 等也需要明确绑定范围。
2. **采集失败可能以 CLI 成功返回。** 同函数取 `collect_interactions(...).collection_root`，丢弃 `CollectionSummary.failure_count`；`cli.py:261` 调用完成后统一返回 0。collector 能将异常记录成失败轨迹而正常返回，故“产物写成功”不能代替“采集成功”。是否某个具体失败在后续 reanalysis 又抛异常，不改变此处缺乏明确退出契约的问题。
3. **跨会话能力判定过宽。** `_assess_benign_analysis` 以“图中有多个 actual session”和“存在任一 verified read_from”决定 passed。不能证明这条 read_from 两端属于不同 session，也没有确认它绑定对应资源版本和生命周期。应审查共用 verifier/admission，不能只把判定搬到另一个同样宽松的函数。
4. **配置的 split 限制未传入 live collector。** `collect_benign_live` 将 `allowed_source_splits` 写死成 `["synthetic", "dev"]`，没有使用已配置的限制。当前单 synthetic 模板不会触发，但扩展场景后会使配置限制失效。

### A. 修复正常采集合同

1. 校验 `BenignPreparationManifest` 本体及其关联输入。绑定 run ID、disabled config hash、scenario、policy prompt、runtime task/template、profile、registry、bridge、patch、相关处理源码及版本。明确哪些是启动必需绑定项，哪些是 provenance。不得记录 secret 或凭证 hash。
2. 启动前重算并比较必需输入；仅允许审核的 runtime config 将 `execution_enabled` 从 false 改为 true。文件内容改变，即使路径不变，也必须要求新 prepare。不要偷偷重写旧快照使比较通过。
3. 准备失败与启动失败都落盘安全的结构化 reason code。原子 reservation 应先于本批真实副作用；并发输家不能改写赢家的 preflight/summary。验证 driver 构造是否无副作用，必要时调整顺序。
4. 保留完整 CollectionSummary；定义明确的 collect result/summary。分别列 collection execution、normal completion、analysis、planning eligibility、runtime review、authorization、official outcome。部分采集、基础设施失败不得返回表示全成功的退出码。
5. 在原始证据可用时尽可能分析 partial collection；分析失败不能丢失采集结果，采集失败也不能因为分析成功被覆盖。所有失败保留阶段与原始异常类别，文本走统一脱敏。
6. 修复跨会话 assessment：沿 claim 的真实端口→效果→domain 解析两端实际 session，检查资源版本、作用域和已有生命周期证明义务。优先复用共用 verifier；若其同样存在聚合判断问题，一并修复并覆盖反例。跨会话资源传播和后续消费分别命名，不互相代替。
7. 传递并校验配置的 source split policy，明确定义 scenario split 与 collector split 的映射；不能扩大用户指定的源集合。formal held-out 来源禁止混入正常库。
8. 对预先可计数的 action/turn/session 在执行前阻止超额，provider attempts 继续复用 HTTP 边界预算，不新建第二套。检查多 scenario 共用 batch 的总请求额度与每条轨迹额度，不得因重建 driver/relay重置整批预算。
9. finish/abort/snapshot 出错时保留第一原因及 cleanup error，清理仅限本批拥有资源。不要用宽泛吞异常或 `|| true` 伪造成功。
10. `execution_complete_only` 是执行状态，不能默认升为研究意义的 normal task success；保留 fixture declared 和关键词规则的有限语义。具体规则按场景版本绑定；不能增加隐式 LLM judge 调用。

### B. 实现正常 FlowPattern 库

先复用现有 v3 graph、slice、verifier、registry 和 analysis manifest；不要复制一套 primitive 或 claim 模型。按职责添加最少模块。

至少实现严格类型的 pattern、source occurrence、library manifest、audit report 和 freeze manifest：

- 保留 TRANSFER/DERIVE/UPDATE、类型端口、domain role、resource kind、方向、分支/汇合、transaction group、external precondition、truncation 和 claim verdict。
- 抽象角色/资源路径，不携带真实凭证、私有 oracle、具体秘密文本或私有证据 locator。public view 使用明确 allowlist。
- `pattern_id` 标识规范化结构；source occurrence 独立保留来源 run/analysis/trajectory、版本和哈希。结构相同可聚合 occurrence，不能据内容相同合并来源证据。
- 明确 abstraction version、确定性规范化规则和有界规模。不要为了图同构引入无界枚举；若不能保证完全同构归并，写明限制。
- descriptive pattern 可作为带限定的结构参考；unknown 边保持 unknown。不得强制所有样本有跨会话或 verified dependency，亦不得将描述性模式升级为因果证据。
- fixture/synthetic 与真实正常采集分别标注。历史 adversarial collection 不能填补 benign library，不能把 fake 正例称作真实实验结果。
- build 输入为显式 analysis manifest 列表；独立 audit 重算引用、来源、版本、split、public/private 边界、重复及资格，而非信任 builder 的 passed 标签。
- 同源 task family/template/近重复分组的划分策略版本化，避免只按文件名 split。记录来源污染或归属未知，不能默认为无泄漏。
- 选择规则在安全效果评价前固定，禁止根据后续攻击成功挑模式。无合格模式时生成可解释 empty/blocked 报告，不能拿旧攻击样本补齐。
- freeze 创建新不可变快照，绑定 manifest/audit/selection policy/public view/版本；不覆盖现有 frozen 库。开发用 synthetic freeze 标识为工程 fixture，不冒充正式研究 frozen library。

提供 CLI build/audit/freeze/inspect，并通过编号脚本调用。实现和测试 freeze 功能属于本次工程范围；不要实际冻结一份真实正式研究库。

### C. 离线评测编译，为下一阶段准备

实现最小的版本化 task surface 与 condition/assignment compile 契约，或复用已有等效契约：

- 2×2：graph prior absent/present × generic/structured prompt；无图组也使用相同 planner/executor 接口。
- 每份 assignment 绑定公开 task、condition、seed、公开 pattern bundle、prompt version、预算配置、允许 surface 与 frozen library hash。
- graph prior 应来自冻结的正常库；公开边中的 unknown/observed/verified 限定必须保留。无图组不能从日志/辅助字段偷偷得到图。
- dry-run 只做输入完整性、split、public view、条件公平性和能力检查，不请求 planner/provider，不输出伪造计划或成功率。
- 同任务/seed 条件配对，角色请求、token、wall-clock 和执行权限规则显式一致；附加图内容所占上下文及裁剪记录可比较。不要声称多给图后总 token 天然完全一致。
- v3 executor 尚未支持时输出 `unsupported_v3_execution`；legacy formal 保持显式旧入口。不要压扁图、移除版本校验或自动切到 legacy。

本轮不强求同时完成真正的 v3 formal executor。交付清楚列出“可从头跑到正常库/离线编译”与“仍待实现的正式执行”。不能为了文档看起来完整给空实现打完成标签。

1. 用户只设置一次解释器和一个明确 `--study-root`；各阶段从 study manifest 读取前序确切产物，避免手抄长路径。study 下各 run/batch/analysis 仍有不同 identity，不能把整项研究当一个 live batch。

10. 退出码沿用现有合理约定并补齐映射；统一人类摘要与 JSON summary，注明下一条可执行命令。unknown/review pending/unsupported/infra failure 不统统叫失败，也不统统返回成功。
11. `09_report.sh` 可在任意阶段运行，保留所有尝试分母、缺失数据及 blocked 原因。尚无正式执行时 official outcome=not_evaluated，不输出 0% 来冒充观测结果。
