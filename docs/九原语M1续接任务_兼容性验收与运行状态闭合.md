## 2. 收紧 P0/P1/P2 的证据验收

先写能暴露误通过的反例，再修改判定。当前判定以 response/state_read 事件存在或 utility=true 为主，不能仅靠事件类型集合决定 passed。

- P1：证明确实对 `trusted/acceptance-ledger.json` 发出了允许的 read，请求与成功结果关联正确，读取内容足以回答问题，工具结果被送入后续模型请求并产生正常最终响应。此处是协议往返，不声称模型语义采纳。拒绝、错误路径、孤立 state_read、无工具结果、结果未返回模型、后续响应失败都不能通过。不得发生写操作。

避免脆弱的模型措辞精确匹配；区分空响应与供应商合法格式差异。模型返回不同措辞不应被当成协议失败。需要新增字段时使用严格模型、稳定 reason code 和生成 schema，避免维护第二套证据系统。

## 3. 闭合运行状态、清理和异常账本

核对 adapter 捕获异常写 runtime_review、runner 根据事件/checkpoint 推导 execution_status、compatibility 写 stage status 三条路径，消除相互矛盾：

- 即使已有有效 checkpoint 或业务效用为 true，随后发生 provider/finish/timeout/cleanup 错误，也保留业务事实，但不能把执行整体报为无异常 completed 或兼容性 passed。
- cleanup_status 必须来自实际拥有资源的清理结果；不能在正常返回分支无条件写 completed。未观察到清理结果为 unknown。
- 失败后的摘要、阶段状态、批次状态和退出码一致；失败或 unknown 不进入下一阶段。status/report 可读取 partial/error 产物，缺文件不能导致其余诊断丢失。
- provider_records 内存变量未填充、finish 失败或 abort 失败时，仍从已有持久 relay 账本恢复实际尝试信息。请求已发送但响应未知应按现有预算语义计入，不允许重置额度；没有证据时不能报告零请求。
- 保留原始异常阶段和脱敏诊断。清理异常不覆盖主异常，也不吞掉清理失败。清理仅针对本 batch 的资源。
- 核对现有累计 8 次门与阶段 1/2/5 门在 HTTP 发送前执行，以及 batch deadline 是否覆盖阶段间续接；配置字段存在不代表机制已经实施。没有实际硬门就修复或明确 blocker，不把事后统计称为硬门。

优先复用已有 deadline、账本、reservation 和清理返回结构。不要引入平行的预算/生命周期框架，不用全局 kill/prune。

## 4. 修正真实事件映射中的来源与身份
